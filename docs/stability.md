# Stability guarantee

This page says what will not change inside a major version, so you can depend on it without reading release notes for breakage. It takes effect at 1.0; the 0.x line has been additive in practice, and `docs/migration-0.x.md` lists everything a 0.x upgrade asks of you.

Six surfaces are covered. Anything not named here is not guaranteed.

## 1. The Go API

Every module in this repository follows semantic versioning, and they share one version number. Within 1.x:

- no exported identifier is removed
- no exported function or method changes its signature
- no exported struct field is removed or changes type
- new identifiers, fields, and options arrive in minor releases

Adding a field to an exported struct is a minor change, so construct them with field names rather than positionally. Adding a method to an exported interface is not: interfaces you implement are frozen for the major.

`scripts/apidiff.sh` compares the exported surface against the previous tag on every pull request and fails on an incompatible change, so this is enforced rather than promised.

Packages under `internal/` in any module are not part of the API and carry no guarantee. That includes every generator: third parties integrate through the external generator protocol in `docs/plugins.md`, not by importing the generator packages.

## 2. The contract document

The document carries its own format version, which moves independently of the library.

- every 1.x reader reads every 1.x document
- new optional fields are a minor format bump; a reader that does not know a field ignores it
- no field is removed or changes meaning within 1.x
- a 2.0 format, if it ever ships, comes with `bowline migrate-contract` converting 1.x documents forward, and readers keep accepting 1.x for the life of the 1.x library line

The normative description is `spec/contract.md`, and `spec/contract.schema.json` validates it.

## 3. Generated code

Regenerating with a newer 1.x CLI, against an unchanged Go module, produces code that compiles against the same major version of every client package. What the generated code does with a given contract does not change.

The layout of generated files may change between minors: formatting, declaration order, and how output is split across files are not guaranteed. This is exactly why generated files are committed and diffed — a regeneration shows up as a reviewable diff instead of a surprise at runtime.

## 4. The CLI

Every command and flag listed in `docs/cli.md` is stable within 1.x. New flags are additive and every new flag has a default that preserves the existing behaviour.

Human-readable output is not stable; do not parse it. The machine-readable outputs are, and they are the ones to script against:

- `bowline check --json`
- `bowline diff --json`, equivalently `bowline diff --format json`

Within 1.x those documents gain fields but never lose them or change a field's type. Exit codes are stable: `0` success, `1` the command ran and the answer is no, `2` the command line is wrong.

## 5. The wire format

Frozen for 1.x, because a client generated by one version talks to a server built with another:

- the response envelope and its error shape
- the sixteen-code set and each code's HTTP status
- `GET` for queries with the input in the `input` query parameter, `POST` with a JSON body for everything else
- server-sent event names for subscriptions, and the heartbeat
- the multipart layout for uploads
- the idempotency key header and its semantics

`spec/mapping-table.md` is the normative mapping from Go types to the wire, and the conformance suite in the `conformance` package is the executable form of this section: any mount that passes it speaks the frozen protocol.

## 6. Support

Release cadence, how long each line receives security fixes, and what qualifies for a backport are in `docs/lts.md`.

## Reporting a break

If a release breaks something this page guarantees, that is a bug, not a migration. Open an issue with the two versions and the smallest reproduction you have. If the break has a security impact, follow `SECURITY.md` instead.
